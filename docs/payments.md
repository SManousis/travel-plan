# Payment sandbox operations

Payment-service stores gateway and payment-method metadata in PostgreSQL when the `infra` profile is active. The default profile keeps a local in-memory store for startup and development. Provider adapters always contact the configured sandbox during method creation or deletion; they do not accept a reference merely because it is nonempty.

## Credentials and reference handoff

Set `STRIPE_SANDBOX_SECRET_KEY` to a Stripe `sk_test_...` key. Set `PAYPAL_SANDBOX_CLIENT_ID` and `PAYPAL_SANDBOX_CLIENT_SECRET` to the credentials of a PayPal sandbox app with vault access. Compose passes these environment settings to payment-service. Supply them through the deployment secret manager; never put secret values in source control. The current implementation uses one configured sandbox merchant account per provider, rather than resolving the `vaultSecretRef` field described by the future OpenAPI contract.

The browser or provider SDK completes tokenization and any payer approval. For Stripe, finish a SetupIntent so the `pm_...` PaymentMethod is attached to a sandbox customer, then send that ID to the admin API. The service retrieves the PaymentMethod, rejects live-mode or unattached objects, and stores only a safe display summary. For PayPal, complete the setup-token approval and exchange it for a vault payment token, then send that payment token ID to the admin API. The service obtains a sandbox OAuth token and retrieves the vault token before marking it active. These requests use bounded HTTP timeouts. See [Stripe PaymentMethod retrieval](https://docs.stripe.com/api/payment_methods/retrieve), [Stripe detach](https://docs.stripe.com/api/payment_methods/detach), [PayPal vault tokens](https://developer.paypal.com/api/payment-tokens/v3/), and [PayPal OAuth](https://developer.paypal.com/api/rest/authentication).

Create a gateway through `POST /api/payment-gateways` with `provider` set to `STRIPE` or `PAYPAL` and a `displayName`. Create a method through `POST /api/payment-methods` with `userId`, `gatewayId`, `providerReference`, and `displayLabel`, plus a UUID `Idempotency-Key` header. The record is persisted as `PENDING` before the provider call. A verified reference becomes `ACTIVE`; a rejected reference or unavailable provider leaves a readable `FAILED` record with a safe failure code. Retry the same request with the same key after resolving the cause. Reusing a key with different input returns `409`.

Only the local display label is editable through `PATCH /api/payment-methods/{id}`. Deletion requires a UUID `Idempotency-Key`; the service marks the method `DELETION_PENDING` before calling Stripe detach or PayPal vault-token deletion, then removes the local row after provider success. Concurrent calls return `202` while a provider call owns the 30-second claim; retry after that window if a process crashed. A failure remains visible as `FAILED` for operator review and retry. A provider `404` is not treated as proof that an old token was removed, because it may belong to an account that the current credentials cannot access. Gateway deletion returns `409 GATEWAY_IN_USE` while any method, including a failed method, refers to it. The API response does not return the provider reference.

## Current limits

No credentialed sandbox exchange has been run in this repository environment. Provider reference inspection verifies the configured merchant account and a reusable/attached token, but the service does not yet establish that the provider customer belongs to the supplied local `userId`. The user-deletion cleanup workflow, per-gateway Vault secret resolution, default-method selection, webhook processing, and the asynchronous operation endpoints/statuses in `docs/api/payments.yaml` remain open. A request that crashes after the provider call may leave a `PENDING` or `DELETION_PENDING` row; retry the same create key or delete request to resume. Do not claim Phase 7's sandbox completion check until both providers have been exercised with credentials and the remaining contract/lifecycle work is complete.
