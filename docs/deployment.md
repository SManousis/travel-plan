# Release deployment

`Jenkinsfile` validates the backend, API contracts, and dashboard before the `main` release stages. A successful `main` build also passes the SonarQube quality gate, builds six application images from the checked-out commit, publishes them with the full Git SHA as the tag, and runs `infra/ansible/deploy.yml` against the selected inventory. Reruns reuse an existing tag only when its image revision label and image ID match the newly built image; a mismatch stops publication. The target uses `compose.yml`, `compose.release.yml`, and `compose.secure.yml`. The release overlay removes application build contexts, so target hosts pull published images instead of compiling source.

## Jenkins configuration

- Provide a Linux agent labelled `travel-plan-ci` with JDK 21, Node.js 22, npm, SonarScanner CLI, Docker CLI and daemon access, Python, Ansible, the `community.docker` collection, and Docker Compose v2. The Jenkins controller in `compose.ci.yml` is only a starting point; it does not provision this agent or plugins.
- Configure the Jenkins SonarQube server as `travel-plan-sonarqube` and the SonarQube webhook as `<Jenkins URL>/sonarqube-webhook/` so `waitForQualityGate` can finish. Install the Jenkins SonarQube Scanner plugin and configure its token in Jenkins credentials.
- Configure registry username/password credentials with ID `travel-plan-registry`. Set `REGISTRY_HOST` (for example `registry.example.org`) and `IMAGE_PREFIX` (for example `registry.example.org/team/travel-plan`). Configure the registry to reject overwriting existing SHA tags.
- Set `DEPLOY_INVENTORY` to a reviewed Linux target inventory. The checked-in `inventory.ini` points to localhost for development and must not be used for a production release by accident.
- Supply `POSTGRES_SUPERUSER_PASSWORD`, `AUTH_DB_PASSWORD`, `USERS_DB_PASSWORD`, `PAYMENTS_DB_PASSWORD`, `NEO4J_PASSWORD`, `AUTH_TOKEN_SECRET` (at least 32 characters), `ADMIN_USERNAME`, `ADMIN_PASSWORD`, and `AUTH_INTERNAL_SERVICE_TOKEN` as protected Jenkins environment values or Ansible variables. Optional sandbox values are `STRIPE_SANDBOX_SECRET_KEY`, `PAYPAL_SANDBOX_CLIENT_ID`, and `PAYPAL_SANDBOX_CLIENT_SECRET`. The playbook rejects missing and known placeholder required values and writes `/opt/travel-plan/.env` with mode `0600`.
- Configure separate Jenkins jobs for pull request validation and the `main` release. SonarQube Community Build in `compose.ci.yml` analyzes only the project main branch, so the PR job runs Maven, API lint, and UI lint/build; the `main` job additionally runs Sonar and release stages. Require the PR job status in Gitea branch protection. Native PR Sonar analysis needs a licensed SonarQube edition.

## Target preparation

The target needs Docker Engine, Compose v2, registry access, and a Python environment usable by Ansible's `community.docker` modules. Provision the TLS files listed in `deploy.yml` under `/opt/travel-plan/tls/certs` before deploying. Use production certificates and appropriate ownership/permissions; `infra/tls/generate-dev-ca.sh` is for local rehearsal only. Set `deployment_health_hostname` to a name on the serving certificate that resolves to the target; `deployment_health_port` defaults to `8443`, and `deployment_ca_path` defaults to `/opt/travel-plan/tls/certs/dev-ca.crt`. The defaults suit local rehearsal (`localhost`), while production deployments should set the matching hostname and CA. The TLS proxy publishes port 8443 on the host; restrict ingress to approved clients with host or network policy. The playbook copies Compose, PostgreSQL and Neo4j initialization files, proxy configuration, and Vault configuration from the release checkout. It logs the target Docker client into the registry, pulls the selected tag, starts the secure stack without building, waits for Java service health checks (including configured database indicators), then checks the HTTPS dashboard and an unauthenticated API request (expected `401`). An authenticated business request remains part of the live audit rehearsal.

The release tag must be a full 40-character commit SHA. To roll back, run the playbook again with a previously published SHA tag, the same `image_prefix` and `registry_host`, and reviewed compatible database migrations. Docker Compose updates services; it does not provide zero-downtime rolling deployment. The playbook does not initialize Vault, issue certificates, rotate secrets, or validate provider ownership. Those procedures remain separate audit work.

## Validation and evidence

Run `ansible-playbook --syntax-check -i <inventory> infra/ansible/deploy.yml` and `ansible-lint infra/ansible/deploy.yml` on the configured agent. Record a clean deployment, a repeat run, a rollback, the exact image SHA tags, HTTPS/backend checks, and any migration outcome in the audit evidence. Source and Compose configuration checks alone do not prove a live release.
